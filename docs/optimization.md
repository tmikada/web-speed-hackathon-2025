# パフォーマンス最適化計画

## プロジェクト概要

Web Speed Hackathon 2025のAREMAという動画配信サービスのパフォーマンス最適化ドキュメント。

- **技術スタック**: React 19 + React Router 7 + Fastify + Webpack
- **評価基準**: Lighthouse + Puppeteer による独自スコアリング（1200点満点）
- **最終目標**: スコアの最大化とレギュレーション遵守

---

## 調査結果サマリー

### アーキテクチャ

```
/workspaces
├── client/    # React 19 フロントエンドアプリ（Webpack）
├── server/    # Fastify SSRサーバー
├── schema/    # DB モデルと API インタフェース
├── configs/   # 設定ファイル群
└── test/      # E2E テストと VRT
```

### 現状の主要な問題点

1. **バンドルサイズ**: すべてのコードが単一ファイルにバンドルされている
2. **キャッシング**: すべてのレスポンスで`cache-control: no-store`が設定されている
3. **SSR**: サーバーサイドレンダリングが正しく機能していない
4. **依存関係**: 未使用のライブラリが大量にバンドルに含まれている

## 最適化ポイント（優先度順）

### 🔴 高優先度

#### 1. Webpackのコード分割が無効化されている

**場所**: `workspaces/client/webpack.config.mjs:62`

**問題**:
```javascript
new webpack.optimize.LimitChunkCountPlugin({ maxChunks: 1 })
```
- すべてのコードが単一の`main.js`にバンドルされる
- ページレベルの動的インポートが実装されているのに、webpackで無効化されている
- React Router 7の`lazy()`が機能していない

**影響**:
- バンドルサイズが極めて大きい
- 初期ロード時に不要なコードもダウンロードされる
- Time to Interactive (TTI) が悪化

**解決策**:
- `LimitChunkCountPlugin`を削除
- ページごと、フィーチャーごとにチャンクを分割
- 動的インポートを活用したコード分割を有効化

**期待される効果**:
- 初期バンドルサイズ 50-70% 削減
- **TBT**: 🔴 大幅改善（JavaScript実行時間の削減）
- **LCP**: 🟡 改善（リソース競合の削減）
- **FCP**: 🟡 改善（初期ロード削減）

---

#### 2. キャッシュヘッダーがno-store

**場所**: `workspaces/server/src/api.ts:17-18`

**問題**:
```typescript
fastify.addHook('onSend', async (_request, reply) => {
  reply.header('cache-control', 'no-store');
});
```
- すべてのレスポンスに`cache-control: no-store`が設定
- 静的アセット（34MBの画像群）が毎回再ダウンロード
- CDN/ブラウザキャッシュが完全に無効

**影響**:
- ネットワーク負荷が極めて高い
- リピート訪問時のパフォーマンスが著しく悪い
- Largest Contentful Paint (LCP) が悪化

**解決策**:
- 静的アセット（画像、フォント、動画）には長期キャッシュを設定
  - `cache-control: public, max-age=31536000, immutable`
- APIレスポンスには適切なキャッシュ戦略を設定
  - 変更頻度に応じて`max-age`を調整
- ファイル名にハッシュを含めてキャッシュバスティング

**期待される効果**:
- リピート訪問時のロード時間 80-90% 削減
- **LCP**: 🔴 大幅改善（画像キャッシュで即座に表示）
- **TBT**: 🟡 改善（ネットワーク待機時間の削減）
- **Speed Index**: 🔴 大幅改善（リソース読み込み高速化）

---

#### 3. SSRが活用されていない

**場所**: `workspaces/server/src/ssr.tsx:54-60`

**問題**:
```typescript
const html = renderToString(<App />);
// ↑ この結果が使われていない

// 実際のレスポンス
<body></body>  // 空のボディ
```
- `renderToString()`の結果を破棄している
- クライアント側で完全に再構築（ダブルレンダリング）
- サーバーとクライアント両方で処理時間がかかる

**影響**:
- First Contentful Paint (FCP) の悪化
- Time to Interactive (TTI) の悪化
- サーバーリソースの無駄

**解決策**:
- `renderToString()`の結果を`<body>`に挿入
- クライアント側では`hydrateRoot()`でハイドレーション
- SSR時にデータプリフェッチを活用

**期待される効果**:
- **FCP**: 🔴 大幅改善（初期HTMLにコンテンツが含まれる）
- **LCP**: 🔴 大幅改善（画像などがSSRで配信）
- **CLS**: 🟡 改善（レイアウトの早期確定）
- **TBT**: 🟡 改善（クライアント側処理の削減）

---

#### 4. 複数ビデオプレイヤーの同時バンドル

**場所**: `workspaces/client/src/features/player/logics/create_player.ts`

**問題**:
```typescript
// 3つのプレイヤーすべてがバンドルに含まれる
- ShakaPlayerWrapper (shaka-player)
- HlsJSPlayerWrapper (hls.js)  ← 実際に使用
- VideoJSPlayerWrapper (video.js)
```
- 実際にはHlsJSのみ使用
- 未使用のプレイヤーで900KB以上増加

**影響**:
- バンドルサイズの無駄な増加
- パース・コンパイル時間の増加

**解決策**:
- 使用するプレイヤー（HlsJS）のみを残す
- または動的インポートで必要な時のみロード

**期待される効果**:
- バンドルサイズ 900KB+ 削減
- **TBT**: 🔴 大幅改善（JavaScript実行時間の削減）
- **FCP/LCP**: 🟡 改善（初期ロードの削減）

---

### 🟡 中優先度

#### 5. Webpack本番最適化が無効

**場所**: `workspaces/client/webpack.config.mjs`

**問題**:
```javascript
mode: 'none',                      // 本番最適化なし
devtool: 'inline-source-map',      // source mapを埋め込み
```
- Tree-shaking、minification、uglificationなし
- Source mapが本番バンドルに埋め込まれる

**影響**:
- バンドルサイズの増加
- 未使用コードの残存

**解決策**:
```javascript
mode: 'production',
devtool: false,  // または 'source-map' で別ファイル化
```

**期待される効果**:
- バンドルサイズ 20-30% 削減
- **TBT**: 🟡 改善（JavaScript実行時間の削減）
- 未使用コードの除去

---

#### 6. Lodash全体がバンドルされている — 対応済み

**場所**: クライアント全体

**対応内容**:
- `lodash/merge` → 手動シャローマージに置き換え（`createStore.ts`）
- `lodash/debounce` → 自前の `setTimeout` ベース実装に置き換え（`createTimetablePageStoreSlice.ts`）
- lodash への依存を完全に除去済み

---

#### 7. ポリフィル（core-js）の全体読み込み

**場所**: `workspaces/client/webpack.config.mjs:25-28`

**問題**:
```javascript
useBuiltIns: 'entry',  // 全ポリフィルを含む
```
- モダンブラウザでは不要な機能が多数

**影響**:
- バンドルサイズの増加

**解決策**:
```javascript
useBuiltIns: 'usage',  // 使用する機能のみポリフィル
targets: '> 0.5%, last 2 versions, not dead',  // ターゲットブラウザを明確化
```

**期待される効果**:
- バンドルサイズ 30-50KB 削減
- **TBT**: 🟢 小改善（パース時間の削減）

---

#### 8. 画像のプリロードすべてに指定

**場所**: `workspaces/server/src/ssr.tsx:76`

**問題**:
- すべての画像（34MB）に`rel="preload"`を指定
- ネットワークリソースの競合が発生

**影響**:
- 初期表示で必要な画像のダウンロードが遅延
- LCP の悪化

**解決策**:
- Above the fold（初期表示に必要）の画像のみプリロード
- その他は遅延読み込み（lazy loading）

**期待される効果**:
- **LCP**: 🔴 大幅改善（重要な画像の優先読み込み）
- **FCP**: 🟡 改善（リソース競合の解消）
- 初期ネットワーク負荷の軽減

---

#### 9. UnoCSS Runtimeとアイコン動的読み込み

**場所**: `workspaces/client/src/setups/unocss.ts`

**問題**:
- 7種類のIconifyコレクションをランタイムで読み込み
- ブラウザで処理される

**影響**:
- Cumulative Layout Shift (CLS) の発生
- レンダリング遅延

**解決策**:
- ビルド時にアイコンを静的生成
- 使用するアイコンセットのみに限定

**期待される効果**:
- **CLS**: 🔴 大幅改善（レイアウトシフトの防止）
- **FCP**: 🟢 小改善（レンダリング時間の短縮）

### 🟢 低優先度

#### 10. 番組表の頻繁なDOM操作

**場所**: `workspaces/client/src/pages/timetable/components/Program.tsx`

**問題**:

- 処理を間引く（throttle/debounce）

**期待される効果**:
- **INP**: 🟡 改善（インタラクション応答性の向上）
- **TBT**: 🟢 小改善（メインスレッド負荷の軽減）
- スクロール時のパフォーマンス改善

## 測定指標とスコアリング

### 採点方法（1200点満点）

#### 1. ページの表示（900点満点）⭐ **最重要**

9つのページをLighthouseで検査し、各ページ100点満点で採点：

**対象ページ**:
- ホーム
- 番組表
- 番組（放送前・放送中・放送後）
- シリーズ
- エピソード（無料・プレミアム）
- 404

**各ページの採点配分**（Lighthouse v10 Performance Scoring）:
- **Total Blocking Time (TBT)** × 30 = **0-30点** ⭐ 最重要
- **Largest Contentful Paint (LCP)** × 25 = **0-25点** ⭐ 最重要
- **Cumulative Layout Shift (CLS)** × 25 = **0-25点** ⭐ 最重要
- **Speed Index** × 10 = 0-10点
- **First Contentful Paint (FCP)** × 10 = 0-10点

**⚠️ 重要**: ページの表示で **200点以上取らないと次の採点がされない**

---

#### 2. ページの操作（200点満点）

4つのシナリオをLighthouseで検査し、各シナリオ50点満点で採点：

**対象シナリオ**:
- ユーザーの認証（ユーザー作成 → ログアウト → ログイン）
- 番組表の操作（カラムの拡大・縮小）
- サービス内回遊1（ホーム → シリーズ → エピソード）
- サービス内回遊2（番組表 → 番組詳細モーダル → 番組 → 関連エピソード）

**各シナリオの採点配分**:
- **Total Blocking Time (TBT)** × 25 = 0-25点
- **Interaction to Next Paint (INP)** × 25 = 0-25点

---

#### 3. 動画の再生（100点満点）⭐ **高優先度**

2つのシナリオをPuppeteerで検査し、各シナリオ50点満点で採点：

**対象シナリオ**:
- エピソードの動画視聴
- 番組の動画視聴

**採点方法**:

ランディング開始から動画が再生されるまでの時間 `t[ms]` として：

```
score = (1 - max(0, t - 800) / (max(0, t - 800) + 3000)) × 50
```

**スコア目安**:
- **800ms以下**: 50点（満点）
- 1300ms: 40点
- 2300ms: 30点
- 3800ms: 20点
- 20000ms以上: 0点

**最適化ポイント**:
- 動画の初回再生までの時間を800ms以下に抑えることが重要
- HLS/DASH プレイリストのロード時間
- 動画チャンクの初回ダウンロード時間

### レギュレーション（厳守事項）

#### ❌ 禁止事項

1. **Google Chrome最新版で機能落ちやデザイン差異を発生させてはならない**
   - ✅ VRT (Visual Regression Tests) がすべてパスすること
   - ✅ 手動テスト項目がすべてパスすること

2. **VRTと手動テストを通過させるためだけの悪意あるコードを書いてはならない**

3. **競技終了後にデプロイしたアプリケーションを更新してはならない**

#### ✅ 要求事項

1. **順位確定までアプリケーションにアクセスできる状態であること**

2. **`POST /api/initialize` でデータベースを初期値にリセットできること**
   - 採点サーバーは初期値を前提に計測
   - データ構造の変更は可能だが、機能落ちは不可

#### 🧪 機能要件（手動テスト項目）

**動画関連**:
- 動画の自動再生（ホーム、番組、エピソード、404ページ）
- 動画品質（著しい劣化がないこと）
- プレイヤーコントロール（再生/停止、音量、シークバー）
- シークバーホバー時のサムネイル表示

**UI/UX関連**:
- カルーセルの横スクロール（カード単位でスナップ）
- モーダルの表示/非表示（番組表、番組詳細、機能紹介）
- ホバー時のスタイル変化（各種カード、ボタン）
- ローディングアニメーション（0.5秒以上かかる場合）

**認証関連**:
- ユーザー登録/ログイン/ログアウト
- バリデーション（メールアドレス、パスワード）
- プレミアムエピソードのアクセス制御

**番組表関連**:
- カラムサイズの拡大・縮小
- 番組詳細モーダル
- 機能紹介モーダル（初回表示）

**⚠️ 最適化時の注意**: これらの機能を壊さないこと。VRTと手動テストで確認される。
